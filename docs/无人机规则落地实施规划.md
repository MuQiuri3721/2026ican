# 基于无人机规则与项目思路的实现规划

## Context

两份方案文档已整理为：

- `docs/无人机子群与参数规则1.md`
- `docs/思路细化.md`

它们冻结了项目的业务目标：2架侦察（R1–R2）+4架灭火（E1–E4）+2架支援（S1–S2）资源池；电量按分钟折算；火情用 FLP 计算；每5分钟反馈重规划；先满足硬约束再评分；用户确认后才执行；有人、无人和信息不确定必须走不同分支。

### 阶段 1：领域契约与兼容适配（P0）

修改 `backend/app/domain/schemas.py`，增加并校验：

- `subgroup`：`reconnaissance`、`suppression`、`support`；
- UAV 状态：`available`、`assigned`、`flying`、`working`、`returning`、`servicing`、`charging`、`fault`；
- `payload_module`：`none`、`water_20l`、`co2_6kg`、`sup_10`；
- `people_status`：`confirmed`、`absent`、`unknown`；
- 任务状态：`queued`、`running`、`awaiting_confirmation`、`approved`、`executing`、`replanning`、`completed`、`terminated`、`failed`；
- `target_minutes`、用户约束、禁用/保留设备；
- 反馈轮次输入：观测火情 FLP、增长率、风速、人员状态、fleet/inventory snapshot。

建立兼容归一化函数：

```text
id → uav_id
role → subgroup
battery → soc
payload → agent_remaining
```

业务规则只读取新字段，旧字段只作为兼容输出。所有响应增加 `schema_version` 和明确单位字段。

**验收：** 新旧 fleet 数据均可读取；非法枚举、负 SOC、超载输入返回 422；旧 API 仍可用。

```text

```

- 任务状态；

### 阶段 3：V1 确定性 Tool（P0）

修改 `backend/app/tools/core.py`，新增工具并保留旧工具兼容包装：

1. `normalize_uav_record`；
2. `get_fleet_status_v1`；
3. `get_inventory_v1`；
4. `calculate_energy_consumption`；
5. `calculate_soc_need`；
6. `check_uav_feasibility`；
7. `select_water_source`；
8. `calculate_flp_load`；
9. `calculate_agent_effective_flp`；
10. `simulate_fire_round`；
11. `simulate_supply_cycle`；
12. `transition_uav_state`；
13. `reserve_resources`；
14. `release_resources`；
15. `calculate_resource_gap`；
16. `score_dispatch_plan`。

冻结公式：

```text
ρ_load = m_task / m_capacity
r = r_mode × (1 + 0.45ρ_load + 0.20f_wind + 0.10f_climb) + r_aux
ΔSOC = r × Δt / 60
SOC_need = SOC_outbound + SOC_task + SOC_return + SOC_reserve
B_i = 10 × I_i × K_fuel × K_wind × K_slope
S = Q_agent × κ_agent,scene × η_drop × η_weather
B_next = max(0, B_now + G×Δt/60 − ΣS)
J = 0.40T_norm + 0.30B_residual + 0.15E_norm + 0.10M_norm + 0.05N_change
```

硬约束：药剂兼容、SOC返航≥25%、载荷不超限、路线可达、健康度合格、人员分支资源保留。植被火默认 W20，电气热点只能 C6；就地取水必须满足可用、安全、容量、路线风险、返航 SOC 和至少节省5分钟。

**验收：** 标准算例可复现；净处置能力不足时返回 `resource_gap`，不输出虚假单点完成时间。

修复当前 `EnvironmentAssessmentSkill` 和后续 Skill 的字段层级不一致，确保真实风速、坡度、水源和道路进入规则。

```text

```

```text
queued → running → awaiting_confirmation → approved → executing

```

```text
任意非终态 → terminated
任意状态 → failed
```

关键规则：

- 生成方案不等于执行；
- 未确认方案不能进入 flying/working；
- 拒绝后释放资源锁；
- 调整约束后生成新版本方案；
- 终态任务禁止继续监测；
- 每次状态变更写入事件。

## 数据结构与 API 契约（实施基线）

### `UAVRecord`

```json
{
  "uav_id": "E2",
  "subgroup": "suppression",
  "status": "available",
  "position": {"x": 120, "y": 80, "z": 0},
  "soc": 92,
  "payload_capacity_kg": 25,
  "payload_module": "water_20l",
  "agent_remaining": 20,
  "agent_unit": "L",
  "speed_mps": 8,
  "energy_rate_percent_per_hour": 270,
  "signal": 88,
  "health": 100,
  "assigned_task": null,
  "last_updated": "2026-09-03T10:00:00Z"
}
```

字段校验必须拒绝负 SOC、负药剂、未知枚举、超过 `payload_capacity_kg` 的任务载荷；`agent_unit` 必须与模块一致（W20 为 L，C6 为 kg，SUP10 为 kg）。位置可使用 x/y/z 或经纬度，但同一任务中必须统一距离计算坐标系。

### `DispatchPlan`

```json
{
  "schema_version": "uav-dispatch-v1",
  "plan_id": "plan-001",
  "task_id": "task-001",
  "generated_at": "2026-09-03T10:00:00Z",
  "risk_level": "high",
  "selected_uavs": ["R1", "E1", "E2", "S1"],
  "agent_allocation": [{"uav_id":"E1","role":"primary","target_cells":["c-01"]}],
  "battery_plan": [{"uav_id":"E1","outbound_soc":8.2,"task_soc":28,"return_soc":8.2,"reserve_soc":10}],
  "water_source_plan": {"source_id":"base","fill_minutes":4},
  "people_branch": "absent",
  "estimated_control_time": {"min":38,"max":45,"unit":"min"},
  "feasibility": true,
  "resource_gap": [],
  "alternative_plan": [],
  "replan_trigger": ["wind_band_changed"]
}
```

> 字段落地差异（2026-09-04）：以上是规划基线示例；**实际输出字段以 `docs/api-contract.md` §7 为准**——任务分配在 `tasks`（无 `agent_allocation`）；无 `risk_level`（风险由 `fire_assessment.level` 承载）；`battery_plan` 条目为 `{uav_id, soc_before, soc_after_return, sortie_soc_cost, sorties, swaps, refills, reserve_percent, state, outbound_minutes}`；`estimated_control_time` 为 `{earliest_minutes, latest_minutes, window_minutes, unit, simulated}`。

### 端点行为

| 端点 | 请求关键字段 | 成功响应 | 必须处理的错误 |
|---|---|---|---|
| `GET /api/fleet` | 可选 `task_id` | 8 架完整状态及 `schema_version` | 数据源不可用返回标记为演示快照 |
| `GET /api/inventory` | 可选场景/补给点 | 水、CO₂、SUP10、电池、水源 | 不返回负库存 |
| `GET /api/tasks/{id}/plan` | 任务 ID、方案版本 | 主/备选方案、约束检查、来源 | 无方案 404 |
| `POST /api/tasks/{id}/approval` | `action`、`plan_id`、可选调整 | 新任务状态、事件、资源锁结果 | 非当前版本 409；非法动作 422 |
| `POST /api/tasks/{id}/rounds` | 新图像、环境/资源快照、轮次号 | `before/after`、changes、triggers、next_action | 轮次倒退 409；终态任务 409 |
| `POST /api/tasks/{id}/replan` | 触发原因、约束覆盖 | 新版本方案和缺口 | 缺少必要观测 422 |
| `GET /api/tasks/{id}/report` | 任务 ID | 输入、版本、轮次、事件、消耗和结论 | 任务不存在 404 |

所有写操作必须生成幂等请求键或版本号，避免重复确认导致重复扣库存。状态、资源锁和库存扣减在同一事务/锁范围内完成；失败时整体回滚。

## 阶段依赖、风险与回滚

### 依赖关系

1. 阶段 1 的 Schema 和兼容归一化是阶段 2–6 的前置条件。
2. 阶段 2 的资源池、库存和锁是确定性 Tool、API 和闭环的前置条件。
3. 阶段 3 的公式 Tool 必须先通过标准算例，阶段 4 才能接入 Skill 编排。
4. 阶段 4 输出稳定的 `dispatch_plan` 后，阶段 5 才开放审批和执行。
5. 阶段 5 的任务状态事件是阶段 6 轮次及阶段 7 前端展示的数据来源。
6. 阶段 8 的端到端验收必须覆盖前述所有阶段，不以单元测试替代真实 API 流程。

### 风险与控制措施

| 风险 | 影响 | 控制措施 | 触发回滚条件 |
|---|---|---|---|
| 旧字段与新字段语义冲突 | 旧接口或前端异常 | 入口归一化、响应保留旧别名、增加版本字段 | 旧 API 回归失败 |
| 并发审批/重复分配 | UAV 或库存被重复使用 | 资源锁、版本校验、幂等键、409 冲突 | 出现重复锁或负库存 |
| 模型输出非结构化/幻觉数字 | 错误调度 | VLM 只输出观察与解释，所有数字由 Tool 计算 | 关键字段无来源或无法复算 |
| 环境数据缺失/过期 | 路线和取水判断错误 | 来源、时间戳、默认值标记；unknown 先侦察 | 缺失数据被当作确定事实 |
| 规则过严造成无可行方案 | 任务无法推进 | 返回 `resource_gap`，提供备选和补给动作 | 方案无缺口说明 |
| 前后端字段不同步 | 页面误导 | 契约测试、统一 Schema、演示位置标识 | 构建或契约测试失败 |
| 真实模型/地图接入延期 | 进度阻塞 | 固定 JSON/GeoJSON、模型适配器和 fallback | Demo 无法完整闭环 |

### 回滚与兼容策略

- 每阶段使用独立 feature flag：`dispatch_v1_rules`、`approval_flow_v1`、`closed_loop_v1`、`dynamic_fleet_ui`；默认关闭新执行链，便于逐阶段启用。
- 保留旧 `/api/monitor/{analysis_id}` 和旧响应字段；旧 `extinguishing_liters` 只在入口转换为 W20 输入，不反向污染新领域模型。
- 新方案按 `plan_version` 保存，不覆盖已确认方案；发生异常时将任务退回最近一个可验证版本，并释放本版本锁定资源。
- 数据迁移前备份 `fleet.json`、`inventory.json` 和内存快照；发现负库存、状态非法或无法恢复事件链时，恢复备份并关闭对应 feature flag。
- 回滚验收必须重新执行旧 API 冒烟、新旧字段兼容、库存非负和任务终止四类测试；不得只回滚前端而保留已扣减的后端状态。

## 每阶段执行清单与验收门槛

| 阶段 | 完成定义 | 交付物 | 阻塞条件 |
|---|---|---|---|
| P0 契约 | Schema、归一化、错误码稳定 | 契约测试、字段字典 | 任一非法输入未拒绝 |

| P0 调度 | 主备方案及缺口可解释 | plan fixture、Skill 测试 | 有人/unknown 分支缺失 |
| P0 审批 | 未确认不执行、事件完整 | API 集成测试 | 状态可越级 |
| P0 闭环 | 两轮对比和触发重规划 | round fixture、回放测试 | 轮次或 SOC 不一致 |
| P1 前端 | 动态 8 机、审批和轮次可操作 | build、浏览器冒烟 | 仍有三架硬编码 |
| P0/P1 交付 | 六个端到端场景通过 | 测试报告、可运行 Demo | 任一关键场景无法闭环 |

## 优先级总结

### P0

契约、2+4+2资源池、库存、状态存储、SOC/FLP/物资规则、硬约束、审批API、5分钟闭环、有人分支、后端测试。

### P1

Vue动态8机、审批界面、轮次对比、报告、地图动态标记。

### P2

真实 YOLO/VLM、视频流、真实飞控、全国GIS、三维火场、多用户权限、数据库持久化。

## 不建议的实现方式

- 不要继续在 `pipeline.py`、Skill 和前端各自计算一遍调度；
- 不要让 VLM 或大模型直接决定无人机数量和关键数字；
- 不要把 CO₂作为开放森林火灾默认药剂；
- 不要把支援无人机描述为空中充电或运送人员；
- 不要把没有 GPS 的演示位置标成真实位置；
- 不要在资源不足时输出没有依据的确定完成时间。
